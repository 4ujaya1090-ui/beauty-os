# Beauty OS — Архитектура

Актуально на: версия с самозаписью клиента (после внедрения ролей, Firestore, графика работы).

## Стек

- React + TypeScript + Vite
- React Router (клиентский роутинг, без сервера)
- Firebase Auth — вход по email/паролю
- Firestore — хранение данных
- Firebase Hosting — публикация (`beauty-os-ae06f.web.app`)
- PWA — устанавливается на телефон как приложение (manifest + service worker)

Storage (фото) и Cloud Functions — **не используются**. Оба требуют платный тариф Blaze, решено отложить (см. ROADMAP.md).

## Модель ролей

Роль не хранится явным полем — она **выводится** из того, какие документы существуют в базе для текущего пользователя:

```
Вошёл пользователь (Firebase Auth uid)
        │
        ├── есть profiles/{uid}?          → он специалист
        │
        ├── есть clients/{X} с authUid=uid? → он клиент
        │
        └── ничего нет                     → недавно созданный аккаунт,
                                              показываем настройку профиля специалиста
```

Специалист в системе сейчас **один**. Данные (`clients`, `procedures`, `appointments`, `articles`, график) не привязаны к конкретному специалисту (`specialistId` нигде нет) — это осознанное решение, не забытая недоделка. Если появится второй специалист, работающий в этой же базе, потребуется отдельная переработка модели данных.

## Как пользователь попадает в приложение

`App.tsx` — единственная точка ветвления по роли:

```
useAuth() → нет пользователя           → LoginPage
useProfile() → пока грузится            → пусто (не мигает)
useRole() → clientRecord существует     → дерево роутов клиента (/, /my/*)
useProfile() → profile существует       → дерево роутов специалиста (/, /clients, /calendar, ...)
иначе                                    → ProfileSetupPage (первый вход специалиста)
```

Два дерева роутов (клиента и специалиста) — независимые `<BrowserRouter>`, у каждого свой корень `/`. Клиент физически не может получить доступ к роутам специалиста — их просто нет в его дереве.

## Модули (`src/modules`)

| Модуль | Отвечает за |
|---|---|
| `auth` | Вход (`AuthContext`), профиль специалиста + график + подписи медкарты (`ProfileContext`), определение роли (`RoleContext`), экраны входа/настройки |
| `clients` | Карточки клиентов, медкарта, создание логина клиенту |
| `procedures` | Прайс-лист (услуги: название, длительность, цена) |
| `appointments` | Календарь, запись на приём, проверка пересечений по времени |
| `articles` | Публикации специалиста (черновик/опубликовано) |
| `clientCabinet` | Экраны, которые видит **клиент**: дашборд, запись на приём, история, статьи |
| `Dashboard` | Дашборд специалиста (`CosmetologistDashboard`) |
| `shared` | Переиспользуемые UI-компоненты (кнопки, карточки, поля ввода) и `HomePage` |

Внутри каждого модуля — единообразная структура: `context/` (данные), `components/` (переиспользуемые кусочки), `pages/` (экраны).

`shared/components/Dropdown` — готовый компонент, сделан заранее, но пока нигде не подключён.

## Провайдеры (`main.tsx`)

Порядок важен — каждый следующий может пользоваться данными предыдущих:

```
AuthProvider              (кто вошёл)
  ProfileProvider          (профиль специалиста, знает свой uid)
    RoleProvider            (клиент это или специалист — использует ClientContext)
      ClientProvider         (список клиентов — только для специалиста)
        ProcedureProvider     (прайс-лист — читают все вошедшие)
          AppointmentProvider  (записи — читают все, пишут по правилам)
            ArticleProvider     (статьи — специалист видит черновики, остальные нет)
              App
```

## Защита данных

Реализована на двух уровнях одновременно — оба обязательны:

1. **В коде** — контексты запрашивают только то, что нужно роли (например, `ClientContext` вообще не делает запрос, если вошедший не специалист)
2. **В Firestore Rules** (консоль Firebase) — окончательная защита; даже если бы код запросил лишнее, база бы отказала

Полный текст правил — см. `DATABASE.md`.

### Осознанные компромиссы (не баги)

- **`appointments`** читают все вошедшие пользователи (не только свои записи) — иначе клиент не смог бы во время самозаписи увидеть, какие слоты уже заняты у других. Клиент видит дату/время/процедуру чужих записей, но не может узнать, чей это визит (карточки клиентов ему недоступны).
- **`comment`** (внутренняя заметка специалиста в записи) технически лежит в том же документе, что читает клиент. В интерфейсе это поле клиенту не показывается, но не скрыто на уровне Firestore Rules (это ограничение самого Firestore — правила работают на уровне документа целиком, не отдельных полей).
